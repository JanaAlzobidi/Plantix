# Plantix

منصة جدولة ذكية لبرامج المعارض. تحل مشكلة فريق البرامج: **إيجاد الموقع والوقت المناسبين لكل فعالية**، بدون تعارض، مع أقل تغيير على ما اعتُمد.

العميل هو المعرض نفسه: المحرك واحد، وكل معرض يضبط أيامه وساعاته وقواعده في ملف إعدادات خاص به.

**المستخدمون الثلاثة:**
- **منظم البرامج:** يراجع المقترح ويعتمده.
- **صاحب الفعالية:** يرفع طلباته ويتابع حالتها.
- **مشرف القاعات:** يبلّغ عن الأعطال.

## شرح الملفات

### المحرك `engine/`

المحرك يأخذ الفعاليات والقاعات والجدول المعتمد، ويرجّع جدولًا مقترحًا. **لا يكتب أي ملف ولا يغيّر المعتمد**، والاعتماد خطوة منفصلة.

| الملف | وش يسوي |
|---|---|
| `__init__.py` | فيه `generate_schedule(programs, venues, approved, reference_date=..., freeze_window_days=...)`، الدالة الوحيدة اللي تحتاجينها من برّا. ترتّب الخطوات: تحقق ← خيارات ← حل ← تقرير. |
| `config.py` | الإعدادات الافتراضية (أيام المعرض، ساعات التشغيل 09:00–18:00، بدايات كل 15 دقيقة) وترتيب الأولويات وتعريف نافذة التجميد `in_freeze_window`، ومعها أسماء الحالات بالعربي. |
| `data.py` | يقرأ ملفات CSV ويتحقق منها: أعمدة ناقصة، أرقام غلط، تواريخ خارج المعرض، فعاليتان ثابتتان متعارضتان. كل مشكلة تطلع برسالة عربية واضحة بدل ما ينهار البرنامج. |
| `candidates.py` | يولّد لكل فعالية كل خيار ممكن (يوم × وقت × قاعة) يحقق القيود الصارمة. إذا ما فيه ولا خيار يشرح السبب: السعة، أو المعدات، أو القاعة تحت الصيانة، أو نافذة التجميد. |
| `solver.py` | يختار من الخيارات أفضل جدول بـ OR-Tools CP-SAT، بدون تداخل في أي قاعة مع احتساب وقت التجهيز، وحسب الأولويات بالترتيب (تحت). |
| `report.py` | يحوّل النتيجة لجداول يقرأها المنظم: الجدول المقترح، وغير المجدولة بالسبب والحل، والتغييرات مقارنة بالمعتمد، والملخص. |
| `storage.py` | الملفات على القرص: يحفظ المقترح في `data/proposal/`، ويعتمده بنقله إلى `approved_schedule.csv` مع نسخة من القديم في `approved_history/`. يرفض الاعتماد إذا تغيّرت البيانات بعد إنشاء المقترح. |
| `client.py` | يحمّل مجلد معرض كامل (`clients/<اسم>/`): ملف `client.json` بقواعده، وبياناته. |
| `profile.py` | يقرأ قواعد المعرض من JSON ويتحقق منها: الأيام، والساعات، والأولويات، ونافذة التجميد. |

**ملف تنبيهات الحضور `engine/insights.py`** (اختياري، ما انرفع للحين): يتعلم من الدورات السابقة ويرسل تنبيهًا إذا فعالية حضور عام متوقع تزدحم أكثر من سعة قاعتها. مكانه داخل `engine/`، والمحرك يشتغل بدونه. يستخدم عمود `category` الاختياري في الفعاليات.

### قواعد الجدولة باختصار

**قيود صارمة، ما تنكسر أبدًا:**
- القاعة متاحة.
- القاعة تتسع للحضور، وفيها كل المعدات المطلوبة.
- الفعالية داخل ساعات التشغيل.
- ما فيه فعاليتان في نفس القاعة بنفس الوقت، ويُحسب وقت تجهيز القاعة بعد كل فعالية.

**الأولويات بالترتيب**، وكل مستوى أهم من كل اللي تحته مجتمعة:
1. لا تُسقط فعالية معتمدة.
2. جدولة أكبر عدد من الفعاليات.
3. أقل تغيير على المعتمد.
4. تحقيق اليوم والفترة المفضلة.
5. أنسب قاعة لحجم الحضور.

**أنواع الفعاليات:**
- **ثابتة:** صاحبها حدد موعدها وقاعتها، والمحرك ما يحرّكها.
- **مرنة:** المحرك يختار لها.

**نافذة التجميد:** الأيام القريبة من اليوم. ما تُضاف لها فعاليات جديدة، وأي تغيير فيها يُعلَّم للمراجعة.

**نوع الحضور:**
- **حضور عام:** العدد تقديري، ويخضع لتنبيهات الحضور.
- **تسجيل مسبق:** العدد مؤكد.

### البيانات `data/`

| الملف | الأعمدة |
|---|---|
| `programs.csv` | `program_id`, `program_name`, `duration_min`, `attendance_value`, `venue_requirements` (المعدات مفصولة بـ `;`), `time_type` (`fixed` أو `flexible`), `fixed_date`, `fixed_start_time`, `fixed_venue_id`, `preferred_dates`, `preferred_time_slots` (مثل `09:00-12:00`). وأعمدة اختيارية: `admission` (`open` أو `registration`) و`category`. |
| `venues.csv` | `venue_id`, `venue_name`, `capacity`, `equipment`, `min_setup_time_min`, `status` (`available` أو `maintenance` أو `unavailable`). |
| `approved_schedule.csv` | `program_id`, `program_name`, `date`, `start_time`, `end_time`, `venue_id`, `venue_name`. |

هذي بيانات العرض الحالية: 18 فعالية و6 قاعات، والنتيجة 15 مجدولة و3 بأسباب واضحة. سيناريو المعرض المصغّر نسويه في الأخير.

### الواجهة

| الملف | وش يسوي |
|---|---|
| `server.py` | سيرفر FastAPI. يشتغل على نسخة من `data/` داخل `runtime/`، فملفات `data/` ما تتغير أبدًا، وإعادة تشغيل السيرفر ترجّع العرض نظيف. كل طلب من الواجهة يشغّل المحرك الحقيقي، وكل تشغيلة أقل من ربع ثانية. |
| `web/index.html` | هيكل صفحة المنظم: الشريط العلوي (الشعار، البحث، أزرار الأدوار، زر النمط) والحاويات اللي يعبّيها `app.js`. |
| `web/styles.css` | **نظام التصميم كامل.** ألوان النمطين كمتغيرات (`var(--primary)`…)، والخطوط، وكل العناصر: البطاقات، والأزرار `btn`، والشارات `chip`، والاختيارات `pill`/`tchip`، والجدول الزمني `bar`، والنوافذ. أي صفحة جديدة تستخدمه كما هو. |
| `web/app.js` | منطق صفحة المنظم: يجيب البيانات من السيرفر، ويرسم الجدول الزمني والجدول، ويفتح التفاصيل والنماذج و«ماذا لو؟» والمراجعة والاعتماد. ما يحسب أي رقم بنفسه، كل شي من المحرك. |

**طلبات السيرفر (API):**

| الطلب | الوظيفة |
|---|---|
| `GET /api/state` | كل شيء: الأيام (وأيها مجمّد)، والقاعات، والفعاليات، والجدول المقترح، وغير المجدولة، والتغييرات، والملخص، والمعتمد. |
| `POST /api/check` | فحص فعالية قبل حفظها: وين بيحطها المحرك، أو ليش ما يقدر. |
| `POST /api/programs` | إضافة فعالية. |
| `PUT /api/programs/{id}` | تعديل فعالية. |
| `DELETE /api/programs/{id}` | حذف فعالية. |
| `POST /api/programs/{id}/lock` | قفل موعد فعالية مرنة أو فكّه. |
| `POST /api/whatif` | تجربة بدون حفظ: `close_venue` أو `open_venue` أو `attendance` أو `hours` أو `add_day`. |
| `POST /api/whatif/apply` | تحويل التجربة إلى المقترح. |
| `POST /api/approve` | اعتماد المقترح. |
| `POST /api/reset` | إرجاع البيانات لأصلها. |
| `GET /api/download/schedule.csv` | تحميل الجدول (يفتح في Excel). |
| `GET /print/venues` | جداول القاعات للطباعة أو الحفظ PDF. |

### أدوات ثانية

| الملف | وش يسوي |
|---|---|
| `run.py` | يشغّل المحرك من الطرفية ويطبع النتيجة: `python3 run.py propose --reference-date 2026-10-15 --freeze-days 2` ثم `python3 run.py approve`. |
| `app.py` | واجهة تجريبية قديمة بـ Streamlit، من قبل الواجهة الجديدة. ما نستخدمها في العرض. |

| الملف | يختبر |
|---|---|
| `test_engine.py` | قواعد المحرك واحدة واحدة: القيود الصارمة، والأولويات، ونافذة التجميد، والأسباب، والتغييرات. |
| `test_against_bruteforce.py` | يقارن المحرك بحل يجرّب **كل الجداول الممكنة** على 400 حالة عشوائية، ويتأكد إن المحرك دائمًا يوصل لأفضلها. |
| `test_client.py` | ملف إعدادات المعرض: نفس الفعاليات تعطي جدول مختلف لمعرض بأيام وساعات مختلفة. |
| `test_server.py` | طلبات السيرفر: الأرقام من المحرك، و«ماذا لو؟» ما تغيّر المقترح، والقفل يثبّت الموعد، والاعتماد، والتحميل. |

## الملفات اللي ما تنرفع على GitHub

موجودة في `.gitignore`، والبرنامج ينشئها لحاله:

- `data/proposal/`: آخر مقترح.
- `data/approved_history/`: النسخ السابقة من الجدول المعتمد.
