# Plantix

منصة جدولة ذكية لبرامج المعارض. تحل مشكلة فريق البرامج: **إيجاد الموقع والوقت المناسبين لكل فعالية**، بدون تعارض، مع أقل تغيير على ما اعتُمد.

العميل هو المعرض نفسه: المحرك واحد، وكل معرض يضبط أيامه وساعاته وقواعده في ملف إعدادات خاص به.

**المستخدمون الثلاثة:**
- **منظم البرامج:** يراجع المقترح ويعتمده.
- **صاحب الفعالية:** يرفع طلباته ويتابع حالتها.
- **مشرف القاعات:** يبلّغ عن الأعطال.

---

## التشغيل

```bash
pip install -r requirements.txt
python3 server.py          # يفتح http://127.0.0.1:8000 (المنظم) و /owner (صاحب الفعالية) و /venue (مشرف القاعات)
python3 -m pytest -q       # الاختبارات، المتوقع: 502 passed
```

## شرح الملفات

### المحرك `engine/`

المحرك يأخذ الفعاليات والقاعات والجدول المعتمد، ويرجّع جدولًا مقترحًا. **لا يكتب أي ملف ولا يغيّر المعتمد**، والاعتماد خطوة منفصلة.

| الملف | وش يسوي |
|---|---|
| `__init__.py` | فيه `generate_schedule(programs, venues, approved, reference_date=..., freeze_window_days=...)`، الدالة الوحيدة اللي تحتاجينها من برّا. ترتّب الخطوات: تحقق ← خيارات ← حل ← تقرير. |
| `config.py` | الإعدادات الافتراضية (أيام المعرض، ساعات التشغيل 09:00–18:00، بدايات كل 15 دقيقة) وترتيب الأولويات وتعريف نافذة التجميد `in_freeze_window`، ومعها أسماء الحالات بالعربي. |
| `data.py` | يقرأ ملفات CSV ويتحقق منها: أعمدة ناقصة، أرقام غلط، تواريخ خارج المعرض، فعاليتان ثابتتان متعارضتان. كل مشكلة تطلع برسالة عربية واضحة بدل ما ينهار البرنامج. |
| `candidates.py` | يولّد لكل فعالية كل خيار ممكن (يوم × وقت × قاعة) يحقق القيود الصارمة. إذا ما فيه ولا خيار يشرح السبب: السعة، أو المعدات، أو القاعة تحت الصيانة، أو نافذة التجميد. |
| `solver.py` | يختار من الخيارات أفضل جدول بـ OR-Tools CP-SAT، بدون تداخل في أي قاعة مع احتساب وقت التجهيز، وحسب الأولويات بالترتيب (تحت). |
| `report.py` | يحوّل النتيجة لجداول يقرأها المنظم: الجدول المقترح، وغير المجدولة بالسبب والحل، والتغييرات مقارنة بالمعتمد، والملخص. |
| `storage.py` | الملفات على القرص: يحفظ المقترح في `data/proposal/`، ويعتمده بنقله إلى `approved_schedule.csv` مع نسخة من القديم في `approved_history/`. يرفض الاعتماد إذا تغيّرت البيانات بعد إنشاء المقترح. |
| `client.py` | يحمّل مجلد معرض كامل (`clients/<اسم>/`): ملف `client.json` بقواعده، وبياناته. |
| `profile.py` | يقرأ قواعد المعرض من JSON ويتحقق منها: الأيام، والساعات، والأولويات، ونافذة التجميد. |

### نموذج توقع الحضور `engine/attendance_model.py`

نموذج تعلّم آلة يتوقع **نسبة الزيادة في الحضور** عن تقدير صاحب الفعالية، ويرسل للمنظم **تنبيهًا احترازيًا** يقبله أو يتجاهله.

- **يتعلم من:** `data/attendance_history.csv`: كل فعالية من الدورات السابقة (2023–2025) بمجالها وفئتها المستهدفة، وكم كان المتوقع وكم حضر فعلًا.
- **يتوقع:** `الزيادة = الحضور الفعلي ÷ المتوقع − 1`. مثلًا 0.52 تعني حضورًا أكثر بـ52٪.
- **المدخلات:** المجال، والفئة المستهدفة، **والمزيج بينهما**. الفعالية اللي لها أكثر من مجال أو فئة تتوزع قيمتها بالتساوي بينها. المزيج هو اللي يخلّيه يتعلم إن «ريادة أعمال × طلاب» تزيد كثير، مع إن ريادة الأعمال مع المستثمرين ما تزيد.
- **الخوارزمية:** Linear Regression من scikit-learn بنسخة Ridge: انحدار خطي مع تنظيم بسيط، عشان مزيج ظهر مرتين بس ما يقرر لحاله.
- **قابل للتفسير:** كل توقع مجموع أجزاء واضحة: متوسط الدورات + أثر المجال + أثر الفئة + أثر المزيج. تظهر في تفاصيل الفعالية.
- **التسجيل المسبق:** عدده مؤكد، فيُستبعد من التدريب وما يتوقع له النموذج أي شي. التوقع لفعاليات **الحضور العام** فقط.
- **تقييم صادق:** قبل التدريب النهائي يتدرّب على 2023–2024 ويُختبر على 2025 اللي ما شافها. الخطأ 6.1 نقطة مئوية، مقابل 18.7 لو صدّقنا تقدير صاحب الفعالية كما هو (R² = 0.83).

**متى يطلع التنبيه؟** فعالية حضور عام مجدولة، والزيادة المتوقعة 15٪ أو أكثر، والعدد المتوقع أكبر من سعة قاعتها. التنبيه يظهر في «يحتاج قرارك»:
- **اقبل التوقع:** يصير الحضور العدد المتوقع، ويعيد المحرك جدولتها في قاعة تتسع. التغيير يدخل المقترح، وصاحبها يُبلَّغ بعد الاعتماد بأن السبب «استيعاب زيادة الحضور المتوقعة».
- **تجاهل:** ما يتغير شي. لو تغيّر عدد الحضور بعدين، يرجع النموذج يفحصها.
- الفعالية الثابتة أو المقفلة: نصيحة فقط («علمت»)، لأن المحرك ما يحرّكها.

البيانات الحالية مولّدة بـ `scripts/make_history.py` وتحاكي سجل دورات سابقة؛ في معرض حقيقي نستبدلها بسجلاته. بدون الملف يشتغل كل شي عادي بدون تنبيهات.

### قواعد الجدولة باختصار

**قيود صارمة، ما تنكسر أبدًا:**
- القاعة متاحة.
- القاعة تتسع للحضور، وفيها كل المعدات المطلوبة.
- الفعالية داخل ساعات التشغيل.
- ما فيه فعاليتان في نفس القاعة بنفس الوقت، ويُحسب وقت تجهيز القاعة بعد كل فعالية.

**الأولويات بالترتيب**، وكل مستوى أهم من كل اللي تحته مجتمعة:
1. لا تُسقط فعالية معتمدة.
2. جدولة أكبر عدد من الفعاليات.
3. أقل تغيير على المعتمد.
4. تحقيق اليوم والفترة المفضلة.
5. أنسب قاعة لحجم الحضور.

**أنواع الفعاليات:**
- **ثابتة:** صاحبها حدد موعدها وقاعتها، والمحرك ما يحرّكها.
- **مرنة:** المحرك يختار لها.

**نافذة التجميد:** الأيام القريبة من اليوم. ما تُضاف لها فعاليات جديدة، وأي تغيير فيها يُعلَّم للمراجعة.

**نوع الحضور:**
- **حضور عام:** العدد تقديري، ويتوقع له نموذج الحضور.
- **تسجيل مسبق:** العدد مؤكد.

### البيانات `data/`

| الملف | الأعمدة |
|---|---|

| `attendance_history.csv` | `edition`, `program_name`, `field`, `audience`, `admission`, `duration_min`, `expected_attendance`, `actual_attendance`. |
| `venues.csv` | `venue_id`, `venue_name`, `capacity`, `equipment`, `min_setup_time_min`, `status` (`available` أو `maintenance` أو `unavailable`). |
| `approved_schedule.csv` | `program_id`, `program_name`, `date`, `start_time`, `end_time`, `venue_id`, `venue_name`. |

هذي بيانات العرض الحالية: 18 فعالية و6 قاعات، والنتيجة 15 مجدولة و3 بأسباب واضحة. سيناريو المعرض المصغّر نسويه في الأخير.

### رحلة طلب الفعالية

1. **صاحب الفعالية يرسل الطلب** من نموذج الإضافة. الطلب **ما يدخل الجدولة**، ينتظر في «يحتاج قرارك» عند المنظم.
2. **المنظم يراجعه:** يشوف التفاصيل كاملة، ووين بيحطه المحرك لو قبله، وتوقع الحضور.
3. **قبول:** يدخل المقترح مثل أي فعالية، ويوصل صاحبه إشعار «قُبل طلبك». وإذا توقع النموذج حضورًا أكبر من القاعة يطلع تنبيه احترازي.
   **اعتذار:** مع سبب اختياري يوصل لصاحبه، ويقدر يعدّل الطلب ويرسله من جديد.
4. **اعتماد الجدول:** يوصل صاحب الفعالية موعدها.

صاحب الفعالية يقدر يسحب طلبه قبل القرار.

### الواجهة

| الملف | وش يسوي |
|---|---|
| `server.py` | سيرفر FastAPI. يشتغل على نسخة من `data/` داخل `runtime/`، فملفات `data/` ما تتغير أبدًا، وإعادة تشغيل السيرفر ترجّع العرض نظيف. كل طلب من الواجهة يشغّل المحرك الحقيقي، وكل تشغيلة أقل من ربع ثانية. |
| `web/index.html` | هيكل صفحة المنظم: الشريط العلوي (الشعار، البحث، أزرار الأدوار، زر النمط) والحاويات اللي يعبّيها `app.js`. |
| `web/styles.css` | **نظام التصميم كامل.** ألوان النمطين كمتغيرات (`var(--primary)`…)، والخطوط، وكل العناصر: البطاقات، والأزرار `btn`، والشارات `chip`، والاختيارات `pill`/`tchip`، والجدول الزمني `bar`، والنوافذ. أي صفحة جديدة تستخدمه كما هو. |
| `web/owner.html` و `web/owner.js` | **صاحب الفعالية** (`/owner`): يختار جهته، ويرى طلباته بحالتها (بانتظار القبول، مقبولة، مجدولة، معتذر عنها)، ويرفع طلبًا جديدًا مع فحص فوري بالمحرك، ويستلم إشعاراته. |
| `web/venue.html` و `web/venue.js` | **مشرف القاعات** (`/venue`): حالة كل قاعة ومعداتها، وبلاغ عن عطل جهاز أو إغلاق قاعة مع معاينة الأثر على الجدول قبل الإرسال، ومتابعة البلاغ حتى الاعتماد والإصلاح. |
| `web/eventform.js` | **نموذج إضافة فعالية** بأقسامه الأربعة: المعلومات الأساسية، والجمهور والمجال، ومتطلبات القاعة، والجدولة (مرن أو موعد محدد). الحقول اللي عليها * إلزامية. تستخدمه صفحة صاحب الفعالية وصفحة المنظم. |
| `web/shared.js` | أدوات مشتركة للصفحتين: الاتصال بالسيرفر، التنبيهات، النمط، قائمة الإشعارات. |
| `web/app.js` | منطق صفحة المنظم: يجيب البيانات من السيرفر، ويرسم الجدول الزمني والجدول، ويفتح التفاصيل والنماذج و«ماذا لو؟» والمراجعة والاعتماد. ما يحسب أي رقم بنفسه، كل شي من المحرك. |

**طلبات السيرفر (API):**

| الطلب | الوظيفة |
|---|---|
| `GET /api/state` | كل شيء: الأيام (وأيها مجمّد)، والقاعات، والفعاليات، والجدول المقترح، وغير المجدولة، والتغييرات، والملخص، والمعتمد. |
| `POST /api/check` | فحص فعالية قبل حفظها: وين بيحطها المحرك، أو ليش ما يقدر. |
| `POST /api/programs` | إضافة فعالية. |
| `PUT /api/programs/{id}` | تعديل فعالية. |
| `DELETE /api/programs/{id}` | حذف فعالية. |
| `POST /api/programs/{id}/lock` | قفل موعد فعالية مرنة أو فكّه. |
| `POST /api/whatif` | تجربة بدون حفظ: `close_venue` أو `open_venue` أو `attendance` أو `hours` أو `add_day`. |
| `POST /api/whatif/apply` | تحويل التجربة إلى المقترح. |
| `POST /api/reports/preview` | أثر بلاغ قاعة على الجدول قبل إرساله. |
| `POST /api/reports` | بلاغ من مشرف القاعات (`equipment` عطل جهاز، أو `closed` إغلاق القاعة)؛ يطبَّق فورًا ويجهّز المحرك خطة بديلة تنتظر اعتماد المنظم. |
| `POST /api/reports/{id}/resolve` | تم الإصلاح: تعود القاعة كما كانت. |
| `POST /api/requests` | طلب فعالية من صاحبها؛ يتحقق من الحقول الإلزامية وينتظر قرار المنظم. |
| `POST /api/requests/{id}/accept` | قبول الطلب: يدخل الجدولة ويُبلَّغ صاحبه. |
| `POST /api/requests/{id}/reject` | الاعتذار عن الطلب مع سبب اختياري (`note`). |
| `DELETE /api/requests/{id}` | سحب الطلب قبل القرار. |
| `POST /api/alerts/{id}/accept` | قبول تنبيه الحضور: يصير الحضور العدد المتوقع ويعيد المحرك الجدولة. |
| `POST /api/alerts/{id}/dismiss` | تجاهل تنبيه الحضور. |
| `POST /api/approve` | اعتماد المقترح، وإرسال إشعار لكل صاحب فعالية تأثرت ولمشرف القاعات. |
| `POST /api/reset` | إرجاع البيانات لأصلها. |
| `GET /api/download/schedule.csv` | تحميل الجدول (يفتح في Excel). |
| `GET /print/venues` | جداول القاعات للطباعة أو الحفظ PDF. |
